+## Follow One Failed Calculation Through Its Caller

+

+

+A business calculation should either return a meaningful value or make failure explicit. A returned zero could mean that no payment is due; it must not secretly mean that the calculation never succeeded. Use the method-contract ideas from Chapter 5 to decide which inputs the calculation accepts, and the control-flow ideas from Chapters 3 and 4 to follow what happens next.

+

+The general pattern below is schematic. Replace the operation, exception type, and response with the policy for the actual task. The braces delimit blocks. `catch (ExceptionType name)` selects a compatible exception and gives that exception a local name. It does not execute after every successful operation.

+

+```text

+try

+{

+    operationThatMayThrow();

+    workThatRequiresSuccess();

+}

+catch (SpecificExceptionType problem)

+{

+    permittedFailureResponse();

+}

+finally

+{

+    workRequiredWhenLeavingThisTry();

+}

+```

+

+There can be several catch blocks, ordered from more specific types to more general ones. Only the first matching catch runs for that thrown exception. A `finally` block is optional, as are catch blocks when a try has a finally. Cleanup is not a substitute for handling the failure, and catching a failure does not restart the interrupted statement.

+

+Consider distributing an invoice amount across a positive number of periods. The method rejects zero periods before division. Its caller knows how to explain that particular argument failure. No file API or collection is needed to understand this example.

+

+

+using System;

+static decimal PerPeriod(decimal total, int periods)

+{

+    if (periods <= 0)

+        throw new ArgumentOutOfRangeException(nameof(periods), "Use a positive period count.");

+    return total / periods;

+}

+static void ShowPlan(int periods)

+{

+    try

+    {

+        Console.WriteLine($"Begin {periods}");

+        decimal amount = PerPeriod(120m, periods);

+        Console.WriteLine($"Amount {amount:0.00}");

+    }

+    catch (ArgumentOutOfRangeException)

+    {

+        Console.WriteLine("Choose at least one period.");

+    }

+    finally

+    {

+        Console.WriteLine("End attempt");

+    }

+}

+ShowPlan(3);

+ShowPlan(0);

+

+

+Read the two attempts separately. For three periods, the call returns 40 and the success message runs. For zero periods, `throw` ends the method before division. Control leaves the unfinished try block, enters the matching catch, and then executes finally. There is no `Amount` line for the failed attempt.

+

+| Attempt | Does the method return an amount? | Runs the catch? | Runs finally? |

+| --- | --- | --- | --- |

+| Three periods | Yes, 40 | No | Yes |

+| Zero periods | No | Yes | Yes |

+| Negative periods | No | Yes | Yes |

+

+The exception is created by `new ArgumentOutOfRangeException(...)`; `throw` transfers control. `nameof(periods)` records the parameter name without duplicating its spelling in a string. Do not catch an unrelated type merely because its name sounds like an error. An unmatched exception continues to an enclosing handler after this finally runs. The statement after the failed call is not resumed.

+

+Printing from finally is used only to make control visible here. In Chapter 9, resource disposal will be a concrete cleanup responsibility. Finally does not mean that a result was produced, and it is not guaranteed to run after process termination or machine failure.

+## See the Collection Before Writing Its Loop

+

+

+A store records quantities for four delivery slots. Four unrelated variables would require four separate names and repeated processing code. An array gives the values one name and a position-based organization. Its length is fixed when the array object is created; its elements can still change. This connects the collection idea to variables: assignment changes a value in a particular slot, while a loop chooses which slot to visit.

+

+Use these schematic forms to distinguish three actions:

+

+```text

+elementType[] name;                         // Declare a variable for an array reference.

+name = new elementType[lengthExpression];    // Create an array and store its reference.

+name[indexExpression] = valueExpression;    // Replace one element of that array.

+```

+

+`[]` after the type describes the array type. Brackets after a variable name select an element. Length counts elements; an index identifies a position. For four slots, the valid indexes are zero through three. Index four is already outside the array.

+

+

+using System;

+int[] quantities = new int[4];

+Console.WriteLine($"Before: {string.Join(", ", quantities)}");

+quantities[0] = 7;

+quantities[1] = 5;

+quantities[2] = 9;

+quantities[3] = 6;

+quantities[2] = 4 * quantities[1] - quantities[3];

+for (int index = 0; index < quantities.Length; index++)

+    Console.WriteLine($"Slot {index}: {quantities[index]}");

+

+

+The first line shows default values after allocation. The later assignment reads indexes one and three, computes `4 * 5 - 6`, and stores 14 at index two. It does not insert a fifth quantity or change the array's length.

+

+| Index | After allocation | After four assignments | After the calculation |

+| --- | ---: | ---: | ---: |

+| 0 | 0 | 7 | 7 |

+| 1 | 0 | 5 | 5 |

+| 2 | 0 | 9 | 14 |

+| 3 | 0 | 6 | 6 |

+

+Read the table by column to see a whole array state, or by row to follow one element. The loop's condition checks `index < quantities.Length` before each read. The semicolons in a for header separate initialization, condition and update. A comma between condition and update is not the syntax for this loop.

+

+An initializer such as `int[] quantities = { 7, 5, 9, 6 };` creates the same four initial values more compactly. Use `foreach` when only the values matter; use an index when the task selects or changes positions. A foreach loop can stop early with `break`, but it does not directly provide the current position for an indexed update.

+## Run a Complete File Lifetime in an Owned Workspace

+

+

+A report has two different identities: its contents and its location. Reading valid quantities from the wrong file is still a failed workflow. Start by constructing one known path, use it consistently, and make ownership of temporary files explicit. This connects Chapter 6's cleanup policy with the stream operations introduced in the preceding section.

+

+`Path.Combine(directory, fileName)` returns a string using the platform's path rules. It does not create a directory or a file. `Directory.CreateDirectory(path)` creates the directory if needed. The general using-statement form is a syntax pattern:

+

+```text

+using (ResourceType name = acquireResource())

+{

+    statementsThatUse(name);

+}

+```

+

+The closing brace marks disposal of the acquired resource. The related declaration form, `using ResourceType name = acquireResource();`, keeps the resource until the end of its enclosing scope. Choose the scope deliberately: a writer must be disposed before another operation relies on its completed output.

+

+This example creates a uniquely named temporary directory owned by this run, writes two lines, closes the writer, reads those lines, closes the reader, and deletes only that owned directory. It does not overwrite a student's report or depend on a preexisting file.

+

+

+using System;

+using System.IO;

+string workspace = Path.Combine(Path.GetTempPath(), "cscs_report_" + Guid.NewGuid().ToString("N"));

+Directory.CreateDirectory(workspace);

+try

+{

+    string reportPath = Path.Combine(workspace, "report.txt");

+    using (StreamWriter writer = new StreamWriter(reportPath, append: false))

+    {

+        writer.WriteLine("Order 101");

+        writer.WriteLine("Units 3");

+    }

+    using (StreamReader reader = new StreamReader(reportPath))

+    {

+        Console.WriteLine(reader.ReadLine());

+        Console.WriteLine(reader.ReadLine());

+        Console.WriteLine($"At end: {reader.EndOfStream}");

+    }

+    Console.WriteLine($"Exists before cleanup: {File.Exists(reportPath)}");

+}

+finally

+{

+    Directory.Delete(workspace, recursive: true);

+}

+Console.WriteLine($"Directory remains: {Directory.Exists(workspace)}");

+

+

+Each using block releases its stream when the block ends, even if processing leaves it because of an exception. The outer finally attempts workspace cleanup after the streams have been disposed. Cleanup can itself fail in a real application; finally does not grant permissions or guarantee that a disk operation will succeed.

+

+| Point in this program | Resource state | What is established |

+| --- | --- | --- |

+| After constructing reportPath | No report opened yet | A location string exists |

+| Inside writer block | Writer open | Lines are being written |

+| After writer block | Writer disposed | Buffered output has been finalized normally |

+| Inside reader block | Reader open | The same path is being consumed |

+| After reader block | Reader disposed | No stream from this example remains open |

+| After finally succeeds | Owned directory removed | The example's temporary files are gone |

+

+`Exists` being true does not prove that the report contains valid business data. Conversely, an exception while opening a missing input does not mean that a report contains zero records. Keep “no readable input” separate from “readable input containing no rows.”
